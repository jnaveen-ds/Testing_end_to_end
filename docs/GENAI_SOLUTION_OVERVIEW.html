App 1 · synchronous

Real-time Chat

Problem statement

Calling the model for every identical safe request wastes latency and tokens. The API must handle concurrent users, scale down while idle, use trusted HTTPS, and roll back safely.

Success

  • First request is MISS; second identical request is HIT.
  • 20 duplicate misses create one model call.
  • Replicas scale and return to zero.
  • Bad revision is diagnosed and rolled back.

How we address it

  1. Container Apps gives Fargate-style managed container runtime.
  2. FastAPI computes a tenant/model/prompt-version-aware cache key.
  3. Managed Redis stores only safe successful output with TTL.
  4. SET NX distributed lock prevents a stampede.
  5. APIM and Container Apps provide managed TLS.
  6. Immutable revisions provide rollback.
React prompt
APIM HTTPS + limit
FastAPI cache key
Redis HIT or Foundry MISS
Answer + usage

Use when: short stateless inference, bursty traffic, reusable safe results. Avoid when: work waits for a person, has non-repeatable side effects, or personalized data is not isolated in the cache key.

App 2 · grounded

Document Q&A

Problem statement

Users need answers based on private documents, with citations, and an honest refusal when the supplied material does not contain the answer.

Success

  • Blob files remain private.
  • Lexical/vector retrieval finds the expected chunk.
  • Known answer cites source metadata.
  • Unknown answer does not hallucinate.

How we address it

  1. Blob is the durable document source of truth.
  2. Documents are chunked with source metadata.
  3. Lexical search is verified before vector search.
  4. Only bounded top-k evidence enters the model prompt.
  5. Citations come from retrieved metadata.
  6. Content Safety is observed separately from retrieval quality.
Ingest: React → FastAPI → private Blob → chunk/embed → AI Search
Ask:    React → APIM → FastAPI → safety → Search top-k → Foundry → cited answer

Use when: knowledge is private/changing and traceable evidence matters. Avoid when: exact transactional data should come from SQL/APIs or access-control metadata is missing.

App 3 · asynchronous + human decision

Approval-gated Agent

Problem statement

Long agent work may need a human to approve the exact plan. It must survive restarts, buffer bursts, expire stale work, retry safely, and preserve an audit trail.

Success

  • FastAPI returns 202 and run ID immediately.
  • Approve continues; reject/timeout executes nothing.
  • Duplicate/changed-plan approval is safe.
  • Queue retry, DLQ, and replay are visible.

How we address it

  1. Durable Functions checkpoints the plan and wait state.
  2. External approval event races a 10-minute durable timer.
  3. Approval binds to user, timestamp, and immutable plan hash.
  4. Service Bus absorbs bursts and caps worker concurrency.
  5. Idempotent transitions prevent duplicate side effects.
  6. Cosmos stores product status/audit and expires lab data.

Cost + latency

  • Redis hit adds milliseconds but removes model seconds/tokens.
  • Queue wait intentionally increases completion time while protecting model quotas.
  • Durable timer uses small function/storage operations and no waiting worker.
  • Cosmos TTL limits storage growth; deletion is asynchronous.

Security

  • Cache key includes tenant/auth scope; never cache secrets/errors.
  • Message expiry is not authorization.
  • Approval binds actor + exact plan hash + deadline.
  • Audit retention TTL must follow legal policy, not convenience.

Use when: work is long, bursty, rate-limited, or approval/audit is required. Avoid when: a short request suffices, approvers are not authenticated, or side effects are not idempotent.

Trust, security, and failure boundaries

Trust path

Browser ─HTTPS─▶ Static Web Apps / APIM
APIM ─HTTPS─▶ Container Apps FastAPI
FastAPI identity ─RBAC/TLS─▶ Azure services
  • No service credentials in React/Vite variables.
  • Application identities receive narrow data roles.
  • Internal workflow/queue endpoints are not public.
  • Approval binds to authenticated actor and plan hash.

Honest failure behavior

  • Redis down → bounded direct model path or explicit failure.
  • Search down → dependency error, never fake grounding.
  • Worker down → queue retains work and UI says queued.
  • Model transient error → bounded retry, never cache failure.
  • Bad revision → readiness/smoke fails; restore prior revision.

Delivery architecture

Feature branch + PR
Required backend/frontend checks
Immutable SHA artifacts
GitHub OIDC deploy
Smoke → activate or rollback
Two different approvals: a GitHub environment approval authorizes deployment; the Agent application's approval authorizes one specific runtime plan. They must not be confused.

Local and CI use fake providers. Azure credentials are short-lived OIDC tokens. Deployed Container Apps use immutable image tags and create revisions so evidence and rollback point to exact code.
